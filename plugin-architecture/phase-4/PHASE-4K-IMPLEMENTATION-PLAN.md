## 1. Executive summary

Phase 4K must connect the existing ownership mechanisms into one terminal application lifecycle, expose `app.destroy()`, remove the empty migration scaffold, and verify the complete product. The architecture already requires asynchronous, idempotent destruction, immediate rejection of new mutations, provider-aware dependency ordering, reverse entry removal, best-effort cleanup and container preservation. These lifecycle obligations remain. The subsequent user-approved decision in §3.2 changes the public construction/Map ownership contract: Tilia always creates and owns its Map, existing external Maps are not supported inputs, and the Map is removed last.

Current composition has three separate lifetime authorities: application foundations, semantic foundation, and Runtime-created plugin roots. There is no public application destroy method. Runtime destruction alone tears down all plugins without retaining live domain providers; calling it as the application destructor would violate Architecture §44. Closing all roots at once would also violate provider/deletion ordering. Use an internal application coordinator with narrowly privileged subsystem operations and existing Scope records, not a second resource registry.

All 26 classified repository plugins are enabled; the disabled list is empty. The main discarded mutable-entry/hub/refresh modules have already been removed. The remaining purge is primarily composition gating, migration-shaped audits, accidental internal exports and stale developer instructions. Approved vendor interaction exceptions and valid semantic helpers remain.

R1–R5 are resolved as approved decisions in §15, with implementation verification still required. Public diagnostic APIs, generic dependency inference, automatic recovery loops and the former caller-map index/cache exception are excluded. Implement after the K0 current baseline and approved normative alignment; no repeated design approval is needed for ordinary private method names or equivalent small integration choices. Accepted asynchronous/idempotent/terminal semantics, the independent editor draft and approved 4J vendor placement remain unchanged. A demonstrated need to change these decisions must be raised for discussion, not hidden in implementation.

## 6. Approved app.destroy() contract

### 6.1 Accepted semantics to implement

Architecture §44 is controlling: asynchronous, idempotent, terminal; destruction makes the app unusable synchronously. No resurrection/reinitialization of that object. Repeated calls must not rerun successful cleanup. Error reporting occurs after independent cleanup attempts, and failure never restores active state.

Distinguish four events: (1) synchronous admission/publication authority loss; (2) cooperative abort/cancel notification; (3) physical resource cleanup; (4) returned promise settlement. An AbortSignal or removed DOM node is not proof of stages 3–4.

Do **not** begin with `pluginRuntime.destroy()` or `semanticController.close()`: the former kills required providers; the latter closes entry resources before ordered semantic removal. Keep captured provider hooks/disposers and existing recorded cleanup available privately while revoking application-facing operational authority. This does not permit cleanup to obtain new resources, reopen public facades or acquire a new public privileged capability (R1).

### 6.2 Approved integration sequence

1. Reserve the shared destruction promise/state **before** invoking abort listeners or other callbacks. Atomically fence lifecycle/bootstrap/semantic publication and mark destroying. Stop queued ordinary lifecycle work; invalidate operational facades and callbacks. Retained providers may perform private cleanup only.
2. Cancel app-input invocations and pending plugin setup immediately. Setup already owns registered effects; eventual setup return cleanup remains observed and cannot publish. Stop ready/bootstrap continuation at each acquisition/commit boundary. Do not await ready as an unconditional prerequisite for destruction.
3. Determine retained provider set from exact domain registrations and **creation, entry and cleanup-residual leases**, then include transitive hard dependencies. Teardown other plugins dependents-first with reverse activation tie-break, attempting every independent cleanup.
4. Terminate selection without a final event; invalidate presentations/interactions using existing hooks/handles. Removing ordinary presenter/renderer plugins must already have withdrawn their effects. Do not add terminal rendering-status events.
5. Cancel and join pending entry preparation/disposer handoffs and serialize with existing entry operations. Remove committed entries in reverse insertion order using `removeRecord` semantics and existing final batched clear notification policy. Already removed entries remain absent; residual cleanup is attempted only under accepted retry safety. Keep providers alive through required disposal attempts.
6. Teardown retained providers/dependency closure dependents-first after required entry cleanup attempts, preserving lease-last. Distinguish registration removal, provider-owned resource cleanup and dependency cleanup. Hold needed captured prerequisites through required/eligible safe attempts. If independence cannot be established, conservatively keep the implicated provider root/hard closure operationally unavailable and report blocked residuals; do not infer arbitrary disposer dependencies or add a new registry. Close proven independent resources. Do not force-release leases, run automatic recovery loops or promise future residual recovery. Final Map removal remains the separate last terminal attempt (R4); its success cannot erase failed cleanup evidence. Required unsettled handoffs are joined before this stage, not converted into settled residuals by timeout.
7. Dispose semantic infrastructure, rendering/controller residuals, typed registrations/channels, UI host roots, stylesheet/base-map/pane resources and core listeners. Close roots at their correct stage; retain failure snapshots even if semantic foundation's normal `dispose()` refuses unresolved entries.
8. Attempt public `remove()` on the Tilia-owned Map last, after the ordered resource cleanup/handoffs. Preserve the caller's container and unrelated page resources; borrowed Map-attached effects end with that Map. Map removal failure is a contextual residual, not permission for private-field recovery. Prior cleanup errors/leases remain truthfully reported even if Map removal succeeds. Finalize the app as destroyed on settled cleanup success/failure and report contextual errors/residuals and detached work (R2/R3).

### 6.3 Settled public and failure details

| Case | Approved policy |
|---|---|
| Repeated destroy | Ordinary repeated calls, including abort-notification reentry, share the reserved promise/outcome and never implicitly retry; prohibited identifiable setup/cleanup lifecycle calls follow the distinct R3 rejection rule |
| During initialization | Abort/fence immediately. R5 policy: an external destroy that wins rejects pending ready with app-destroyed; a bootstrap failure that wins preserves its original failure. Ready does not wait for cleanup, and destroy does not wait for ready; already settled ready is not rewritten |
| During installation/resolution | Queued use/unuse reject; resolution may finish as data, no setup/commit; pending setup follows accepted detached rollback |
| Pending async work | Await resource-specific obligations only; observe guarded resource-free work without blanket settlement barrier |
| After destruction | `destroy`, the stable ready/whenReady outcome and terminal plugin discovery remain callable; no new public diagnostic method; operational entry/domain/selection/rendering/load/map getters reject; `hasPlugin` false and `listPlugins` empty as terminal discovery |
| Raw map previously obtained | Borrowed access to a Tilia-owned Map; no ownership transfer or post-destroy survival. Map-attached effects end with Map.remove; creator-owned external work needs its own cleanup. No revocation/sandbox guarantee |
| Fresh app on same page | After successful cleanup, create a distinct app and Map through createDefaultTiliaApp on the preserved container. No reuse of the old Map/app, external-Map initialization, or recreation guarantee with unresolved removal residuals |
| Reentrant cleanup call | Ordinary repeated/abort-listener calls share the promise; identifiable prohibited setup/cleanup lifecycle entry rejects per R3 before returning that promise. Asynchronous self-await cannot generally be detected; document the prohibition, without a new general detector |

### R1 — Operational fence and retained cleanup prerequisites (K1/K2)

Application operational authority and physical Scope liveness differ during ordered shutdown. Apply one private composition admission/publication predicate to existing app/plugin facade calls, registry visibility/callback admission, final create/update/visibility commits and retained-root acquisition entrances. Prevent cached external capabilities and retained Scope child/defer/track/stage/commit/guard entrances from starting new application work after the fence. Inherit the private check through application-owned roots/children; keep standalone Scope semantics unchanged. Captured close/dispose/unsubscribe/release and eligible existing residual cleanup remain callable; no public cleanup privilege or generic guard bypass.

Use bounded internal interfaces with existing records: Runtime stop-admission/selected-teardown/finalize reuses its state, queue, metadata and ordering; DomainRegistry supplies exact existing registration/owner/lease evidence; EntryStore supplies stop-publication/preparation-and-FIFO drain/private remove-and-residual operations. Do not unconditionally skip lease preflights or invoke public clear/retry through a dead facade. Match registration.owner to Runtime controller.scope with exact identity/existing ancestry. Compute the hard closure from current metadata without the installation planner's active-skip shortcut; no second dependency graph or owner registry.

Track preparing create records in existing private EntryStore record storage (the existing entries map is the default implementation). Register the candidate before provider invocation; public list/get/domain views remain active-only. Promote it inside the callback-free commit block, with insertionSequence assigned only at commit. Precommit failure keeps the unpublished record in existing private storage until rollback and lease release or residual recording complete; public views remain active-only. Terminal drain joins creationDone for every captured record, including a rollback already underway, before deciding provider retention. Remove the unpublished record only at creation completion, retaining failed cleanup in the existing residual storage. Never delete a committed entry merely because requester cancellation arrives afterward. Reserve existing disposer/awaitable handoff before provider invocation and use captured controllers/tasks/FIFO tails for drain.

Residual prerequisites are held through required and eligible existing safe cleanup attempts. Do not attempt automatic resource-level inference from arbitrary disposer closures. If remaining resource independence cannot be proved, conservatively withhold physical cleanup of the implicated provider root/hard closure, make it operationally unavailable, and record identities/blocking causes as residuals. Close proven independent roots/records, never force-release leases and never run unbounded waits/retry loops for settled failures. Required never-settling preparation is a distinct accepted awaitable obligation and can keep destroy pending. No public app retry/recovery promise is added; final Map removal is still required by R4 after actual awaited work and independent attempts, without erasing failures or promising that failed cleanup becomes recoverable afterward.

Focused external-provider diagnostics demonstrated that premature dependency-manager disposal prevents a captured entry disposer from completing safe cleanup; retaining the dependency allowed existing cleanup and lease release.
